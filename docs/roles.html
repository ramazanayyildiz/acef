Product managers and product owners

Move from an idea to a coherent, approved delivery unit

Use ACEF before implementation when the user, value, expected behavior, scope, or risk is still unclear.

1

State the outcome

Name the user, problem, desired result, constraints, and explicit non-goals.

2

Explore the journey

ACEF maps activities, edge cases, affected surfaces, and open product decisions.

3

Check readiness

Acceptance criteria and risks are tested for ambiguity before engineering begins.

4

Approve the slices

Large work is split into coherent units. You approve scope, trade-offs, and exclusions.

You bring

User problem, business goal, constraints, deadlines, known risks, and decisions already made.

ACEF returns

A readiness verdict, user journey or story map, acceptance criteria, risk flags, scope split, and next recommended action.

You decide

Scope expansion, priority, risk acceptance, irreversible actions, non-goals, and whether a proposed split still delivers value.

Example request

“We want team billing for account owners. Before implementation, map the complete user journey, identify product decisions and risks, write acceptance criteria, and split the work if one delivery unit crosses too many boundaries. Do not write code yet.”

Useful product and planning skills

spec-readiness checks whether the brief is actionable. storymap maps activities and delivery slices. acef-specify prepares or imports detailed requirements and design for planning-heavy work. ACEF selects them as needed; see the skill catalog.

Developers and technical leads

Make the smallest correct change and prove the real result

Use ACEF for implementation, defect repair, technical discovery, code review, test creation, and release preparation.

1

Describe the change

Give the expected outcome, current behavior, reproduction, constraints, and affected area if known.

2

Confirm the route

ACEF reads the repository, finds proven patterns, and explains the workflow and safeguards.

3

Build narrowly

The agent implements within the agreed scope and runs focused checks while the patch is changing.

4

Review and close

The changed surface is verified, findings are bounded, and the result is reported with evidence.

You bring

Desired behavior, a reproduction when available, technical constraints, forbidden areas, and relevant history that changes the decision.

ACEF returns

Route rationale, affected-surface map, implementation, focused tests, independent verdict when required, and explicit follow-up items.

You decide

Architecture trade-offs, dependency additions, compatibility breaks, destructive operations, and meaningful scope expansion.

Example request

“The avatar disappears after profile editing and returns after a second refresh. Reproduce both states, find the root cause, make the smallest project-native fix, add focused regression coverage, and commit when the relevant checks pass. Record unrelated failures without investigating them.”

Useful engineering and review skills

acef-adapter and map-codebase ground work in repository evidence. bug-hunter and implementation-shape-review provide bounded, report-only review lenses. acef-release-adapter prepares release and rollback evidence. See the full engineering catalog.

QA engineers and testers

Choose coverage from user risk, then automate at the right layer

Start by saying whether this is a new feature, a coverage gap, a release regression pack, or a project with no accepted test pattern.

1

Choose the scenario

New project, new feature, known defect, coverage gap, or regression suite.

2

Map behavior

Turn the user journey into paths, preconditions, alternate states, failures, and expected outcomes.

3

Classify risk

Prioritize permissions, data, sessions, queues, providers, concurrency, and high-impact branches.

4

Deliver evidence

Create a test plan, executable suite, automation, or coverage audit using the project’s real stack.

You bring

The target journey or release, personas, environments, known defects, supported platforms, and what is already covered.

ACEF returns

A flow map, prioritized cases, risk profile, manual checklist, automation mapping or test code, and a regression pack when requested.

You decide

Release-blocking severity, platform matrix, acceptable residual risk, manual versus automated coverage, and final exploratory scope.

Example request

“Build a regression plan for password reset. Cover request, delivery, successful reset, expired and reused tokens, unknown accounts, session behavior, rate limits, and mobile browser behavior. Show prioritized cases and the recommended automation layer before writing test code.”

Which test pipeline should I use?
  • No test suite: start with test-strategy, map critical journeys, then establish one accepted pattern with acef-test-bootstrap.
  • New feature: map or document its flow, plan cases, classify risk, then generate unit/integration or browser tests.
  • Coverage gap: start with test-coverage-auditor, then classify and fill only the prioritized gaps.
  • QA deliverable: use flow-suite-composer to assemble the reviewed plan into an executable regression pack.
