From request to proof

ACEF adds judgment before it adds process.

Every request passes through the same four questions: What kind of project is this? What exactly is changing? How risky is it? What evidence would prove the result?

Step 1

Understand the project before changing it

ACEF reads the repository as evidence. It looks for the real commands, tests, architecture, conventions, and working examples relevant to the task.

How it is built

Languages, frameworks, modules, dependencies, and boundaries.

How it is verified

Focused test commands, CI conventions, and the surfaces users or systems reach.

How this repo solves similar work

A proven example already in the repository—not a generic template from another project.

How ACEF remembers a repository

ACEF can create a project adapter and code map: a compact, evidence-based description of the stack, commands, architectural boundaries, proven examples, and patterns that should not be copied. These records are refreshed when the repository changes materially; they are not regenerated for every task.

Step 2

Choose the smallest workflow that fits

ACEF first asks whether its controls are needed at all. If they are, it chooses the delivery depth and the risk safeguards separately.

Project workflow

Contained, reversible work with one clear boundary.

Focused fix

A reproduced defect with a narrow, known outcome.

Standard delivery

A scoped change that needs a short, traceable lifecycle.

Planned delivery

Large, ambiguous, or planning-heavy work.

Normal checks

The verification expected for the selected workflow.

or
Extra safeguards

Stronger evidence and independent checks for high-risk boundaries—without repeating the workflow.

Official names and exact admission rules are explained on the Workflows page.

Step 3

Build in the project’s own context

The implementation follows the repository’s working patterns and stays inside the agreed scope. Planning or review artifacts are not allowed to expand a small task into unrelated repairs.

Focused context

Each worker receives the current task, the relevant repository facts, allowed paths, verification commands, and a stop condition—not the entire project history.

Clear ownership

For higher-assurance work, the agent that builds the change is not the only agent allowed to approve it.

Scope is part of correctness. If one request contains several unrelated root causes or crosses too many technical boundaries, ACEF splits it before implementation rather than treating one huge story as a virtue.
Step 4

Verify the result where it is actually used

A green helper test is not enough when the change is consumed through a browser, API, queue, database, command, webhook, or another runtime surface.

Focused checks while building

Run the smallest tests that prove the current change. Do not repeatedly run the broad suite during implementation.

One proportionate closeout

Confirm the changed surface and run broader regression once only when the workflow or shared-contract risk requires it.

What “real surface” means

If code writes durable data, another process must be able to read it. If a public page changed, the reachable page must render the intended result. If authorization changed, the actual protected entrypoint must allow and deny the right callers. The required proof depends on what consumes the change.

The user experience

You see decisions and evidence—not internal ceremony

A useful ACEF update should tell you what path was chosen, why, what changed, what was verified, and what—if anything—needs your decision.
