Advanced · exact contracts

Technical reference

This page names the internal contracts, thresholds, state records, and compatibility rules. If you are new to ACEF, start with Start here, then use the role playbooks or skill catalog.

Routing contracts

Admission, execution, and assurance

ACEF routing has three decisions. Historical A–F request categories may still appear in old research, but they are not the execution-workflow model.

DecisionTyped valueContract
AdmissionNATIVE_WORKFLOWReversible, contained work with one technical boundary and one product surface; no ACEF run artifacts
Executionquick-fixACEF Fix: focused red/green evidence, one developer, one independent reviewer, deterministic closeout
ExecutionlightweightACEF Standard: scoped ordinary delivery with a compact traceable lifecycle
Executionfull-bmadACEF Full: one coherent planning-heavy contract using the BMAD v2 lifecycle
Assurancebaseline / guardedGuarded is additive and cannot duplicate the selected execution lifecycle
Native execution speed contract

Native work uses no subagents, at most three distinct focused verification commands, two attempts per identical command, 180 seconds per focused command, and ten active minutes. Recognized tests run through .acef/bin/acef-native-test -- <focused-command>. Broad verification is forbidden during implementation and may run once at closeout on a clean worktree.

ACEF admission triggers

Start ACEF when the work needs controls for persistence or migration, security/privacy/permissions, money, provider integration, realtime behavior, concurrency/fencing, state machines, tracking/reporting/analytics, a new pattern, multiple boundaries or surfaces, irreversible effects, or multi-session/worker coordination.

ACEF Fix contract

New Fix runs use quickFixContract: single-review-v1. The lifecycle is one developer, one independent reviewer, focused red/green and revert-proof evidence, then deterministic closeout. Guarded may strengthen evidence and scope controls; it does not add Process Judge, Patch Assurance, Verify-Patch, Test Review, or a second review cycle.

Lifecycle map

Eight possible phases—not eight mandatory phases

A workflow selects only the phases it needs. This phase map explains artifact ownership; it is not a checklist every task must execute.

PhasePurposeTypical output
1 · Brief and routeClarify the outcome, topology, reversibility, and riskIntake decision
2 · RequirementsDefine user-visible behavior and acceptance criteriaRequirements
3 · DesignResolve architecture, data flow, contracts, and risksDesign
4 · PlanningSplit coherent delivery units and trace them to requirementsStories/tasks
5 · ImplementationBuild against repository-grounded patternsProduct/test change
6 · Review and testVerify acceptance, behavior, boundaries, and changed surfacesEvidence and verdicts
7 · ReleaseApply real CI/CD, rollout, and rollback contractsRelease evidence
8 · FeedbackTurn measured failure into a rule, test, or workflow correctionRetrospective/change

Fix and native work usually use only framing, implementation, and focused verification. ACEF Full may use the full planning sequence. Release and feedback run only when the request includes them.

ACEF Full

How BMAD v2 fits

BMAD supplies the detailed planning and delivery lifecycle for ACEF Full. ACEF provides admission, risk assurance, repository grounding, runtime enforcement, evidence, and cumulative process limits around it.

Generate once

If BMAD already produced requirements, architecture, or stories, ACEF imports and enriches them. It does not regenerate a second version of the same phase.

One coherent contract

Full is not a container for independent defects, unrelated audit findings, or an entire epic implemented as one story.

Full v3 actor separation

New Full runs use fullFlowContract: four-actor-v3. Core story identities are ATDD, Development, Code Review, and report-only Patch Assurance. A Story Process Judge appears only for ambiguity, waiver, evidence conflict, or gate anomaly; the Epic Process Judge remains independent.

The conductor coordinates and owns transitions. It does not author implementation or approve its own work. A builder cannot be the only approver.

Compatibility Full v2

An existing Full active-run record without fullFlowContract remains compatibility six-actor-v2, retaining Verify-Patch, Test Review, and Story Process Judge. This compatibility behavior is not the default for new runs.

BMAD availability

ACEF calls work “BMAD” only when the real BMAD conductor and required skills resolve. Generic subagents imitating BMAD do not satisfy the contract. If the runtime is unavailable, ACEF stops rather than silently substituting a fake Full lifecycle.

Objective supervisor

Exact limits for repeated delivery attempts

Every new admitted run binds to a stable parent objective. Its normalized scope fingerprint prevents renaming r2, recovery, or the story itself from resetting cumulative budgets.

SignalResponse
5 runs, 3 replans, 6 review cycles, or 30 active control minutes without a product/test commitCONSOLIDATING: later admissions must reference the objective defect ledger
Attempted 8th run or 5th replanSUSPENDED_OVER_BUDGET: human-approved scope split required
Manual QA findingChecklist must complete before non-critical findings are explicitly batched by a shared key
Security, payments, migration, realtime, concurrency, or state-machine defectCannot be batched, deferred, or legacy-quarantined; requires Standard/Full + Guarded

Same-run remediation retains the existing maximum of two delta-review cycles. The objective supervisor does not add reviewer roles or another lifecycle.

Worktree freshness handshake

Installed targets record source-runtime and installed-runtime digests. New active runs, supervisor dispatch, status, next-action, pre-commit, and validator checks fail when the installed bytes differ or the source runtime changed after installation.

scripts/update-acef-installation --repo /path/to/target --all-worktrees
.acef/bin/acef-process-validator --repo . --check installation-freshness
Durable process state

Evidence, actors, and authorization

Markdown explains the chronology. Typed JSON state controls what may happen next and binds claims to actors, commands, Git state, output hashes, and approvals.

Core state records
  • docs/ai/ACEF_ACTIVE_RUN.json: workflow, assurance, scope, objective, phase, active actor, and next transition.
  • docs/ai/objectives/<id>.json: cumulative attempts, replans, reviews, defects, manual QA, and progress counters.
  • docs/ai/ACEF_ACTIVE_LEDGER: selects the delivery ledger when more than one exists.
  • Actor, worker-scope, evidence, report, approval, repair, and gate sidecars bind each lifecycle claim.
Fresh session commands

acef-status summarizes installation, active workflow, objective counters, blockers, and warnings. acef-next returns the next allowed action, write boundary, required evidence, forbidden actions, and stop condition. Agents should reconstruct from these typed views instead of broadly rereading old ledgers.

Capability truth levels

ACEF reports the smallest honest state: documented-only, specified, wired, enforced, proven, or installed. Documentation alone cannot be reported as implementation.

Repository grounding

Adapters, patterns, and surface proof

Project adapter and code map

The project adapter records stack facts, commands, test setup, CI/release behavior, architectural boundaries, relevant working examples, and known do-not-copy patterns. A code map supplies repository orientation. Both are evidence-backed and refreshed when covered source paths change materially.

Reuse before create

A “proven example” is grounded at the symbol and behavior level—not copied blindly at the file level. Signatures, return shapes, boundaries, and consumer expectations must match before reuse.

Done = surface-proven

acef-closeout-verify derives required evidence from the adapter’s surface registry. Persistence requires a fresh read from another process; reachability is separate from isolated rendering; unknown surfaces fail closed; and a story cannot downgrade a surface owned by its goal. Browser, HTTP, queue, storage, mail, webhook, command, and library contracts require different evidence.

Installation

Repo-local tools and guards

Install or refresh ACEF in a target repository 
scripts/update-acef-installation --repo /path/to/target

# Refresh every linked worktree after ACEF runtime changes
scripts/update-acef-installation --repo /path/to/target --all-worktrees

The updater installs repo-local tools, schemas, workflows, skills, and the guard contract, then records the source and installed runtime digests.

Claude Code, Codex, and OpenCode guard

scripts/install-acef-bmad-guard --repo /path/to/target installs repository-local hooks and the pre-commit gate. The optional --global-dispatcher installs a small machine-level dispatcher that forwards only to repositories with a local guard. Restart the agent harness after installation.

Validate the installation 
.acef/bin/acef-process-validator --repo . --check installation-freshness
.acef/bin/acef-status --repo .
.acef/bin/acef-next --repo .
Repository truth

Where to verify a claim

  • AGENTS.md — short routing and enforcement entry point.
  • Delivery rules — normative lifecycle rules.
  • ACEF Full / BMAD v2 contract — detailed Full workflow.
  • Capability records — implemented layers, evidence, limitations, and maturity.
  • Changelog — human-readable framework history.
Core rule: ACEF claims are not evidence. Repository files, validators, tests, installed hooks/tools, and runtime evidence are the evidence.
